## 准备输入

先建立任务卡：

| 字段 | 需要记录的内容 |
|---|---|
| 问题 | 待证明命题、待解释现象、设计目标或实现故障 |
| 条件 | 已知假设、数据、规模、接口、资源和先修结果 |
| 未知量 | 待求对象、待选方案、待验证机制或待修复行为 |
| 完成判据 | 证明闭合、误差界、对照改善、测试通过或解释覆盖 |
| 来源状态 | 已核实、待核实、用户提供、当前独立推出 |
| 检查条件 | 可用的代数、数值、实验、代码和实现环境 |

宽泛主题需要先改写成可判定任务。允许用异常、缺口、争议命题、比较条件、资源约束或交付物作为入口。

## 早期来源检查

在深入推导前完成一次范围适中的来源检查：

1. 找到原论文、正式文档、代码仓库或其他一手来源。
2. 记录已知结果、标准基线、常用记号和已报告限制。
3. 标出当前问题与既有工作的重合、差异和可能的优先权风险。
4. 把来源事实与当前独立推导分开保存。
5. 对无法访问、时效性强、有争议或涉及优先权的主张明确标记状态。

早期检查用于避免重复发现被误写成原创，并为独立推导设置边界。保持检索范围与任务相称，避免用文献罗列替代问题求解。

## 默认主链

### 1. 转换表示或观察对象

当当前形式阻碍推导、解释或实现时，依次检查：

- 能否改写为等价形式或新的目标函数；
- 能否改变参数化、坐标系、基底或优化变量；
- 能否切换为几何、概率、谱、信息量或资源视角；
- 能否把全局对象分解成低维子空间、局部组件或接口状态；
- 能否构造退化输入、极限或反例，使隐藏条件显现。

每次转换后回答：

1. 新对象是什么？
2. 哪项困难得到降低或显式化？
3. 下一步因此能够计算、证明、构造或检查什么？

只改符号、只给类比或只换叙述顺序不构成有效转换。

### 2. 由目标与约束构造

把要求拆成可操作清单：

- 希望保持或达到的性质；
- 必须满足的等式、不等式和不变量；
- 可接受的误差、近似与稳定性范围；
- 计算、显存、时延、数据和接口成本；
- 能判定失败的反例、阈值或测试。

随后让清单决定公式、算法、实验变体或实现结构。对每个设计选择写出它对应的条件。先提出方案再补充宽泛优点时，只能记录为事后解释。

### 3. 连接两条主线

优先采用以下闭环：

```text
原对象与障碍
  → 新表示
  → 新表示暴露的性质或误差
  → 构造条件
  → 候选方案
  → 匹配检查
  → 局部结论与范围
```

允许回到前一阶段。检查失败时，更新导致失败的假设、表示、约束或方案，保留状态变化依据。

## 匹配检查

按主张类型选择证据：

| 主张类型 | 优先检查 | 常见不足 |
|---|---|---|
| 数学命题 | 完整证明、第二路线、边界情形、反例 | 多条路线共享同一隐含假设 |
| 数值性质 | 高精度核对、极端输入、误差与稳定性分析 | 随机样例遗漏最坏情形 |
| 经验主张 | 对照、消融、重复实验、跨规模或跨任务结果 | 单次实验被推广到一般规律 |
| 工程行为 | 可运行测试、故障输入、资源测量、协议检查 | 代码片段被当作完整验证 |
| 来源主张 | 一手来源、原文上下文、版本和日期 | 转述被当作原创或当前事实 |

图表、代码和引用只有在直接支撑当前主张时才构成检查。无法执行检查时，写成待执行计划并避免完成时态。

## 条件机制

### 特例或近似

仅在简化产生结构性洞见时启用：

1. 说明简化了哪个变量、维度、极限或条件；
2. 完成局部推导；
3. 返回一般情形，说明保持条件、误差、代价或推广障碍；
4. 缺少范围恢复时，把结果标为局部或边界。

### 失败反馈

仅在存在真实、可定位反馈时启用：

```text
原假设或方案 → 检查 → 反馈 → 改动位置 → 新结果
```

区分实际反馈与事前风险。事前非凸性、成本或不稳定性判断可以指导预防性设计，不得写成已经发生的失败。

### 系列状态恢复

仅在当前子问题实际依赖前文时启用：

1. 恢复当前步骤所需的定义、公式、条件和未决项；
2. 说明前文停在何处；
3. 明确本篇或本次解释增加什么。

系列编号、链接或背景历史不能单独触发该机制。

## 后期来源检查

完成主要推导后再次检索：

1. 核对新出现的关键词、等价形式和相邻方法；
2. 检查独立推导是否已有公开来源；
3. 复核原创、首次、改进、统一等强表述；
4. 补充遗漏的相关工作、反例和已知限制；
5. 更新贡献主体、证据类型和结论范围。

独立得到已有结果时，可以如实写“独立重构”或“独立推出后发现已有工作”，并给出来源。

## 接口侧重点

- `explore`：保留问题状态、候选路线、检查反馈与最强局部结果。
- `explain`：从原工作的问题进入，重建必要推导，清楚区分来源贡献与当前解释。
- `draft`：把已完成的推理依赖转成文章顺序，避免把事后整理伪装成真实研究过程。
- `revise`：先修复技术和证据缺口，再调整结构与表达；保留原稿中有效的用户贡献。
